# confession — week 2: the data model

## What this is

The Postgres schema and typed query/action layer for مصارحة (confession),
implemented exactly as frozen in
[`docs/SPEC-week2-data-model.md`](docs/SPEC-week2-data-model.md). The whole
point of this slice: **the anonymity claim is a schema decision, not a
feature.** The recipient can never see who sent a confession; the admin can,
and every time the admin looks, that look is logged, in the database, in a
way the application layer cannot suppress or edit.

This is TypeScript + Drizzle ORM against Postgres 17 dialect, per
`work/confession-app/STACK.md`. There is no Next.js app, no UI, and no
Facebook Login in this slice — see "What is NOT built yet" below.

## What this slice covers

- `src/schema.ts` — Drizzle table definitions for `accounts`,
  `terms_acceptances`, `links`, `confessions`, `admin_reveal_log`,
  `link_blocks`, `reports`, `send_counters`, `reveal_offers`,
  `reveal_answers`.
- `drizzle/0000_*.sql` — generated by `drizzle-kit generate` from the schema
  above (tables, columns, foreign keys).
- `drizzle/0001_constraints.sql` — hand-written: every CHECK constraint,
  every PL/pgSQL trigger, and the deferred constraint trigger that makes "an
  offer without a recipient answer is impossible" true at COMMIT, not just
  in application code. drizzle-kit does not emit PL/pgSQL, so this file is
  not generated (spec §3). Every constraint in it carries a comment naming
  the promise it keeps.
- `src/views.ts` — read-only query functions: `getInboxForRecipient`,
  `getPendingOfferForSender`, `getAdminInbox`. The recipient-facing and
  admin-facing row shapes are two structurally different TypeScript types
  built by two different SQL queries — never one query with a field deleted
  afterwards (STACK.md rule 1).
- `src/actions.ts` — mutating functions: `adminReveal`, `sendConfession`,
  `openRevealOffer`, `acceptRevealOffer`, `declineRevealOffer`.
- `src/errors.ts` — the typed rejections for the send path and the reveal
  state machine.
- `src/limits.ts` — the rate-limit constants (`MAX_PER_LINK_PER_HOUR = 5`,
  `MAX_PER_ACCOUNT_PER_DAY = 30`).
- `test/*.test.ts` — all 22 tests from spec §4, numbered in their test names
  (e.g. `4.3.5 ...`) so they can be matched back to the spec. They run
  against a **real Postgres engine** — `@electric-sql/pglite` (Postgres
  compiled to WASM) — with the actual migration files in `drizzle/` applied
  in order by `test/harness.ts`. No mocked database, no `drizzle-kit push`.

## How to run the tests

```bash
npm ci
npx tsc --noEmit   # typecheck
npm test           # applies drizzle/*.sql to a fresh PGlite instance, runs all 22 tests
```

No external services, no Docker, no network access, no environment
variables are required. Everything runs in-process; PGlite is an
in-memory/WASM Postgres, torn down at the end of each test file.

## What this slice deliberately does NOT do (spec §5)

- **No Next.js pages, no Facebook Login, no UI.** Auth is represented purely
  as "an `accounts` row exists"; the OAuth flow is a later slice and needs
  Meta App Review.
- **No deploy.** Nothing is rented until Sam says yes to the €5.99/month
  Hetzner box (STACK.md). This slice runs entirely in-process, in tests.
- **No moderation dashboard.** `getAdminInbox` and `adminReveal` are the
  primitives a dashboard would be built from, not the dashboard itself.
- **No analytics of any kind**, by design — an analytics SDK on the send
  path is the most likely way the anonymity model gets broken by accident.

## Notes on a few implementation choices

- **`sendConfession`'s blocked-sender path returns a success-shaped result
  and writes no row**, per spec §2: a blocked sender who receives an error
  learns that he is blocked, which tells him the recipient acted on him.
  The returned `confessionId` is a random UUID not tied to any database row
  — there is deliberately nothing to look it up against.
- **`getPendingOfferForSender` throws once an offer has left `pending`**
  (declined, resolved or cancelled). This isn't separately numbered in
  spec §4, but it follows directly from the function's own name and from
  test 15's requirement that a declined offer's staked answer is never
  shown to the sender: there must be no live read path back to it at all,
  not just an empty one.
- **`reveal_offers` legal-transition trigger**: the spec's state machine
  (§1) never has any state leave `resolved`, `declined`, or `cancelled`.
  The trigger in `drizzle/0001_constraints.sql` enforces this by rejecting
  *any* `UPDATE` on a row whose current state is not `pending` — which
  covers all three "terminal → anything" cases in test 17 with one rule,
  named in the code comment.
- Rate limiting reuses the single `send_counters` table for both the
  per-link-per-hour and per-account-per-day checks: the per-link count is a
  direct row lookup, and the per-day total for an account is
  `SUM(count)` across that account's hourly rows for the current day. No
  second table was introduced beyond what spec §1 lists.

## Open questions / things worth flagging

None of the 22 required tests were impossible to build as specified, and no
constraint in the spec had to be weakened. Two minor judgement calls were
necessary because the spec describes them by name/intent rather than by
exact mechanism, and both are called out in the "implementation choices"
section above and in code comments at the point they're made:

1. Whether `getPendingOfferForSender` should still return data for a
   non-pending offer (spec's numbered test 11 only exercises the pending
   case). Decided: no — see above.
2. The exact SQL shape of the `reveal_offers` legal-transition trigger
   (spec says "a `BEFORE UPDATE` trigger enforces the legal transitions"
   without specifying every transition explicitly). Decided: once state
   leaves `pending`, the row is fully locked against further `UPDATE`.
